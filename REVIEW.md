# Review instructions — code-config

Reviewer-facing policy for this repo. Read it before any other input: it carries
the operating point and the voice posture every finding must satisfy. The
review-loop rules are org policy and are appended by each reviewer from its own
copy — `resolve_review_md` in knightwatch-reviewer, `_src_rubric` in
seed-auto-roborev's `ref/sync-review-config.sh` for roborev — so they are not in
this file.

## Current thrust

Make the agent's review loop converge in fewer rounds, and shrink the corpus while doing it. Weigh additions against § Review priority's higher bar for added prescription; this names what that bar is currently for.

**Deferring:** new measurement machinery in the corpus — *not* author-side scope control, which is a different control from the reviewer's. `loc-trend.sh` in knightwatch-reviewer reports to the reviewer, whose only remedy is a comment; an author-side ledger reports to the author, who can still decline the round, restructure, or not open the PR. Both should exist. Defer a *new* surface that changes neither the actor nor the remedy. `claude/CLAUDE.md` § Concise Code (the author-side policy, pre-open and per push), `PR_LIFECYCLE.md` § Open (the expected-size declaration Step 6.8 reads), and `babysit-pr` § Step 6.8 (its per-round measurement) are the sanctioned author-side surfaces, `loc-trend.sh` the reviewer-side one — point a new surface at whichever of these already owns its side and job rather than adding another.

**Thrust cadence:** last stated 2026-07-31; restate when the push changes — a trigger of its own, independent of § Product context's. A stale thrust is worse than none, since it anchors every review to a goal nobody holds.

## Product context

**Stage:** Personal engineering-config repo for one engineer (srosro). Holds the canonical copies of `~/.claude/*.md` (coding standards, review practices, testing rules, the auto-tuned `COMMENT_REVIEW_MISTAKES.md`), symlinked into `~/.claude/`. Claude skills live under `claude/skills/`; Codex guidance and skills live under `codex/AGENTS.md` and `codex/skills/`, symlinked into `~/.codex/` and `~/.agents/skills/` respectively. Not a product.

**Distribution model:** Private on GitHub; personal/internal usage. Other engineers may reference it; nobody depends on it as a versioned dependency.

**Architectural commitments:**
- `claude/` and `codex/` are canonical sources of truth; `~/.claude/`, `~/.codex/`, and `~/.agents/skills/` symlinks point in. PRs that move or rename their files break those symlinks on every host using this layout — outsized blast radius for what looks like a simple file move.
- `claude/COMMENT_REVIEW_MISTAKES.md` is **auto-tuned** by `learn-from-replies.sh` (in knightwatch-reviewer), which commits + pushes a fresh top-48 ranked list. The timer (`pr-reviewer-learn.timer`) fires hourly, but `learn-from-replies.sh` exits before rebuilding unless that tick carries a *not-yet-seen* `/srosro-memorize` request (a seen-key dedup is what keeps an already-consumed one from re-firing) — an hourly *check*, not an hourly rewrite. When it does rebuild, the regeneration is wholesale, not a merge. The other `.md` files (`CLAUDE.md`, `CODING_STANDARDS.md`, `REVIEW_PRACTICES.md`, `TESTING.md`) are hand-curated and the auto-tuner explicitly does not touch them.
- Skills under `claude/skills/` and repo-native skills under `codex/skills/` are prompt-engineering artifacts — review them as prompts, not as code. Superpowers remains upstream-owned and is consumed through its pinned Codex plugin.
- Files-and-symlinks model. `just install` symlinks `claude/*.md` + `claude/skills/` into `~/.claude/`, `codex/AGENTS.md` + repo-owned `codex/rules/*.rules` (execpolicy denies, e.g. the `git worktree add` hard stop) into `~/.codex/`, repo-native `codex/skills/` into `~/.agents/skills/`, the `tc` CLI into `~/.local/bin`, and `tmux.conf` to `~/.tmux.conf` — all symlinks-into-the-repo (same model, several target dirs; `tc`'s `lib/` helpers resolve relative to the symlink target). It also adds a guarded line sourcing the repo's `aliases.sh` to the active shell's rc (`$SHELL` — `~/.zshrc`/`~/.bashrc`, created if absent) plus any other rc already present (the `goclaude` launcher: `git checkout main && git pull --ff-only origin main && claude --dangerously-skip-permissions`) — the shell analog of the symlink model (the rc points at a repo-canonical file); `goclaude` is an interactive alias rather than a `~/.local/bin` symlink, and named uniquely (not `cc`) so it never shadows the system C compiler. Host-local install side effects *outside* the symlink model: (1) `setup-playwright-mcp.sh` (run by `just install`) registers the pinned Playwright MCP server in `~/.claude.json` and provisions a Chromium per platform, so the `playwright` skill works without manual per-host setup; (2) one atomic `jq` merge into `~/.claude/settings.json` writes both `claude/hooks/hooks.settings.json` (the hook block — directive capture, knightwatch's in-flight gate, and the repo-owned roborev Claude gates, append-and-dedupe) and `claude/settings.deny.json` (the `permissions.deny` `git worktree add` hard stop, unioned); (3) the default Claude plugins (`superpowers`, `test-kitchen` + their marketplaces) installed via the headless `claude plugin` CLI into `~/.claude/plugins/` + `~/.claude/settings.json`; (4) the official Superpowers Codex plugin, installed from `obra/superpowers` at release `v6.3.0` commit `b36e0829c6d0140e93cfef2ca599b1b07d4a7797` via the headless `codex plugin` CLI into Codex's machine-local config/cache, replacing the stale curated registration; (5) the opt-in `just install-roborev` compatibility route — *not* run by base `just install` — installs roborev's binary, user daemon, and native Git hooks through the frozen legacy installer, then restores code-config's Claude hooks and skill (see `INSTALL.md` Step 6); and (6) the `xterm-ghostty` terminfo entry `tic`'d into `~/.terminfo` so the terminal resolves and tmux can start (fail-soft, skipped where `tic` is absent) — note OSC 8 hyperlink *passthrough* is enabled by `~/.tmux.conf`'s `set -as terminal-features 'xterm-ghostty:hyperlinks'` override, NOT by terminfo `Hls` (tmux doesn't derive it; verified 3.6b). Plugin steps are idempotent and `CONFIG_SKIP_PLUGINS=1` skips them. The `~/.tmux.conf` symlink (added to the model above) carries that override plus `mouse on`. Keep new config in the symlink model unless it genuinely needs host-local state — see `INSTALL.md` for these surfaces. The test harness is `just test`: `./smoke-install.sh` plus `tests/test-*.sh` shell units, sanity-checking the symlink layout (docs, skills, the `tc` entrypoint), fleet behavior, installer plugin contracts, and hook behavior; there is no build or CI.

## Review priority

**Stage:** srosro is a startup founder, you are a pragmatic principal engineer helping him find product-market fit.

**Cultural emphasis:** SIMPLIFY at all costs — complexity kills PMF iteration. Subtractive remedies (delete, collapse, retire) are higher-leverage than additive ones at any severity; cumulative additive LOC across review rounds is the structural-failure signal. See `claude/CODING_STANDARDS.md` § Broken-Glass Test § Subtractive remedies are higher-leverage than additive ones for the canonical policy + worked PR#47→#50 example.

**Repo-specific review emphasis:**
- **Personal engineering-config repo.** Single operator (srosro). Not a product. Holds the canonical copies of `~/.claude/*.md` (coding standards, review practices, testing rules, the auto-tuned `COMMENT_REVIEW_MISTAKES.md`); changes here cascade to every PR reviewed across every tracked repo.
- **`COMMENT_REVIEW_MISTAKES.md` hand-edits:** a hand-edit isn't *automatically* overwritten, since most hourly ticks are no-ops (§ Product context has the gate), so don't flag one as doomed — but do flag its *durability* unless a generator-side fix is landing in a companion PR or filed and linked in the PR. A one-time repair of a bad entry is legitimate; a *durable lesson* parked here is not — that belongs in `REVIEW_PRACTICES.md` or `CODING_STANDARDS.md`, where it's stable and fenced.
- **New or modified skills:** ask whether the change adds guardrails (constraints, refusal conditions, must/must-not rules) or only adds instructions. Pure-instruction skills tend to drift; guardrail skills hold up. Review skills as prompts, not as code.
- **Editorial findings on prose `.md` files are fair game:** internal contradictions, redundancy with another file, ambiguity that would let a reviewer wriggle out of the rule.
- **Architecture findings respect the "files + symlinks, no tooling" commitment** — don't push toward a packaging/install-script rewrite unless the PR proposes it. The repo's test harness is `just test` — `./smoke-install.sh` plus `tests/test-*.sh` shell units — which sanity-checks the symlink layout and the fleet-CLI resolver/picker behavior; treat that as the operating point, not a stepping stone toward CI.
- **Standards-file edits that ADD prescription text are higher-bar than edits that delete it.** Adding "the reviewer must also check X" calcifies a branch every PR review must execute thereafter. Deleting a stale rule, collapsing two redundant rules into one, or replacing a prescriptive list with an inquisitive question is net-leverage-positive. When in doubt, ask what the standards file would look like with this rule removed; if it would still hold up, the addition isn't earning its place.
